# User working rule

Always ask the user what to do and how to do it before taking any action. Never act on your own assumptions or personal judgment — no code changes, commits, pushes, file edits, or any other action without the user's explicit approval first.

# Hero block background animation — working, confirmed on-device

The hero background animation is finalized and confirmed working by the client on a real phone. Do not rework this without explicit request.

- **Mobile (<700px, `style.css` inside `@media (max-width: 700px)`):** the WebGL mesh-gradient shader is skipped entirely (too heavy/unstable on weak mobile GPUs — see the comment in `hero-shader-background.js`). Instead, three blurred radial-gradient blobs (`.hero::before`, `.hero::after`, `.hero > .hero-glow`) drift via CSS `transform`/`@keyframes` (`hero-mobile-blob-a/b/c`), compositor-only, no canvas.
- **Deliberate exception to reduce-motion:** the sitewide `@media (prefers-reduced-motion: reduce)` rule kills all animations by default, which silently froze these blobs for any visitor with that OS setting on (this is exactly what the client saw and reported). The client explicitly asked for this specific decorative effect to keep playing regardless — `style.css`'s reduce-motion block re-enables `animation-duration`/`animation-iteration-count` for those same three selectors on purpose. Keep that exception; don't "fix" it back to respecting reduce-motion without asking first.
- **Desktop/tablet (>700px):** the WebGL shader in `hero-shader-background.js` is a hand-rolled reproduction of the original `@paper-design/shaders-react` `MeshGradient` component (verified against the real npm package v0.0.77). `baseFrame`/`overlayFrame` advance at `0.3`/`0.2` per ms of delta — this must match the original component's `speed` props (base MeshGradient `speed=0.3`, overlay `speed=0.2`); it was previously miscopied as `0.9`/`0.6` (3x too fast) and has been corrected.
- When testing locally, remember `server.js` serves the **built** `_site/` output, not the raw source files — run `npm run build` after editing `style.css` or `hero-shader-background.js` before testing locally, or changes won't show up.

# Hero tags marquee (`.hero-tags` / `.hero-tags-track`) — working, confirmed

The scrolling row of pills ("ТОП-техники", "Видео-уроки", etc.) in the hero is finalized. Do not rework without explicit request.

- **Markup:** `index.html`/`ua/index.html` hard-code **3 duplicate copies** of the 5 tags inside `.hero-tags-track` (15 `<span class="hero-tag">` total, copies 2 and 3 marked `aria-hidden="true"`). This is required, not decorative padding — with only 2 copies, pausing the marquee (hover) near the loop-reset point on wide viewports revealed the real end of the content (looked like it "ran out"). 3 copies guarantees a full screen of buffer content at every scroll position; verified by forcing `transform` to the exact reset point (`-33.3333%`) and the midpoint (`-16.6666%`) and confirming the visible strip stays fully covered both times.
- **Keyframe:** `@keyframes hero-tags-marquee` loops to `translateX(-33.3333%)` (one third, matching 3 copies) — **not** `-50%`. If a copy is ever added/removed, this fraction must change to `-100% / (number of copies)` or the loop will skip/stutter.
- **Edge fade:** `.hero-tags` has `mask-image: linear-gradient(90deg, transparent, #000 8%, #000 92%, transparent)`. This value was tuned deliberately — wider (e.g. 16%) was tried and made the pills look washed out/hard to read most of the time; narrower (6%) made the cutoff look too abrupt. 8% is the balance point. Don't widen it again to try to hide a "looks like it ends" complaint — that's what the 3-copy buffer above is for; the fade only needs to soften the immediate edge.

# Gold ribbon ticker (`.ribbon` / `.ribbon-wrap` / `.ribbon-track`) — working, confirmed

The diagonal-look gold band that crosses the hero/next-section seam is finalized. Do not rework without explicit request.

- **Straddles the seam on purpose:** `.ribbon-wrap` lives as a sibling **between** `</section class="hero">` and `<section id="program">` in the HTML (not inside `.hero`, which clips overflow) and uses `margin: -20px 0` so the band visually overlaps both the dark hero and the cream section below it, per the client's explicit request.
- **No `rotate()` — use `clip-path`-free flat band instead.** A real `transform: rotate()` on a full-bleed-width element needs a taller bounding box as the viewport widens (excursion ≈ `width * sin(angle)`), which caused two rounds of bugs: clipping on wide screens, and a mismatch where mobile crossed the seam by ~3px while 1920px+ crossed by ~20px+ (looked completely different by device). A `clip-path` fixed-px diagonal was tried next and also rejected — geometrically it produced identical height at both edges (verified by pixel sampling), but a rectangular screenshot crop near the top edge still *looked* asymmetric because one corner sits a few px lower than the other by construction. The current version has **no tilt at all** — a flat rectangular band — which is the only version that is identical at both edges under any crop/framing, not just in theory.
- **`.ribbon-wrap` has no `overflow` property.** Do not add `overflow: hidden` (or worse, mixed `overflow-x`/`overflow-y`, which computes to `auto` on the mismatched axis and paints a real scrollbar — this exact bug shipped once already). `html`/`body` already have `overflow-x: clip` globally, which is what actually prevents `.ribbon`'s `-40px` bleed from causing a horizontal scrollbar; `.ribbon-wrap` doesn't need its own clipping.
- **Edge fade is on `.ribbon-wrap::before`/`::after`, not a mask on `.ribbon`.** These are gold-to-transparent gradients painted on top, fixed at the visible edges (they don't scroll with `.ribbon-track`). This fades the ticker *text* into solid gold at the edges without making the gold background itself transparent — masking `.ribbon` directly was tried first and would fade the background too, which isn't wanted here (unlike `.hero-tags`, which has no background of its own to preserve).
- **Ticker items live in `site-core.js`** (`ribbonTrack`), built from an array of 8 strings duplicated **2x** (`[...items, ...items]`, 16 spans total) with a `scroll-left` keyframe looping at `-50%` — matches 2 copies, unlike the hero-tags marquee which needed a 3rd copy (see above) to avoid a visible "end" when paused. This hasn't shown that same symptom, but if it ever does, the fix is identical: add a copy and change `-50%` to `-100% / (number of copies)`.
- Verified clean (no clipping, no overflow, consistent seam-crossing, no scrollbar) from 320px through 2560px, RU and UA, via automated measurement — not just eyeballing a couple of breakpoints.
